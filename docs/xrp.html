1. Kit contents and assembly checklist

Paul has two boards. The XRP V1 (SparkFun XRP Controller: RP2350 + Radio Module 2, USB-C, DRV8411A drivers) is the primary vision-test robot. The XRP Beta (Pico W/RP2040, Micro-USB, DRV8835 drivers) is the spare/second robot. Both run the same WPILib XRP firmware release, but each needs its own UF2 (§3). The robot code (§5) is the same on both.

Encoder/motor channel numbers in WPILib terms are identical on both boards, so one robot.py drives either one. Run the 10-turn count check (§6) on each robot and keep a separate constants file per robot.

Checklist (follow the XRP User Guide assembly, up to and including mounting the arm to the servo):

  • ☐ Chassis plates / snap-fit parts
  • ☐ 2 hobby gear motors with built-in encoders (6-pin cables): Motor L and Motor R connectors
  • ☐ 2 wheels (60 mm dia, with O-ring tires) and the caster/skid
  • ☐ 4xAA battery holder with a barrel plug into the controller's barrel jack
  • ☐ XRP controller board
  • ☐ Reflectance (line) sensor, on the Line 4-pin connector
  • ☐ Ultrasonic rangefinder, on DIST/RANGE ("ping"-style sensors only work on that port)
  • ☐ Servo + arm, on Servo 2 (per SparkFun)
  • ☐ Cable routing: keep motor cables clear of the wheels and the caster; leave the top deck clear for the Pi/camera; reach to the USB port for flashing
  • ☐ A USB data cable (USB-C on V1, Micro-USB on Beta)

2. Power

  • Barrel jack input: 4.8 V minimum recommended, 11 V maximum. The 4xAA pack is at most about 6 V.
  • NiMH rechargeables are recommended by WPILib. 4x NiMH gives about 4.8–5.6 V and sags less under motor load. Alkaline starts at about 6 V but sags hard at high current.
  • The power switch cuts battery input. It does not cut power to the processor when USB is plugged in (both boards).
  • V1: fused barrel jack; a single 5 V buck regulator, about 3 A total; a LOW VOLT LED wired to the buck's POWER_GOOD, which lights when the input sags below the regulator threshold (SparkFun: "not technically a low battery indicator" but it tracks low AAs). VIN is measured on GPIO46. Beta: 5 V minimum input, no LOW VOLT LED, VIN on GPIO28.
  • Low battery: expect weaker or uneven drive, then a Wi-Fi drop or reboot under motor load. There's no documented auto-shutdown or low-battery alarm in the WPILib firmware (UNVERIFIED). Log the battery voltage; the WPILib XRP firmware reports it to the sim GUI/RobotController (UNVERIFIED: v2.1.0 release notes don't list battery voltage among the WPILib-exposed channels; RobotController.getBatteryVoltage() may report a sim default). Swap batteries below about 4.6 V under load (UNVERIFIED, a rule of thumb).

3. Firmware (WPILib XRP UF2)

Source: GitHub wpilibsuite/xrp-wpilib-firmware → Releases → latest v2.1.0 (published Oct 17 2025) → Assets. v2.1.0 is the first release that supports the V1 (RP2350) board. Re-check for a newer release before flashing.

V1 (primary)

  1. Download xrp-wpilib-firmware-2.1.0-aa439f0.uf2 (the file without -beta).
  2. Plug USB-C (data cable) into the controller.
  3. Hold BOOT, press and release RESET, then release BOOT. Or hold BOOT while plugging in USB.
  4. A mass-storage drive appears. It should be named RP2350 (UNVERIFIED; SparkFun only says "mass storage device").
  5. Drag the UF2 onto it. The board reboots and the drive disappears.

Beta (spare)

  1. Download xrp-wpilib-firmware-beta-2.1.0-aa439f0.uf2.
  2. Plug Micro-USB into the Pico W. Hold BOOTSEL, tap RESET, release BOOTSEL.
  3. Drive RPI-RP2 appears. Drag the UF2 on. It reboots.

A wrong-board UF2 just won't install (WPILib docs).

First boot (both)

  • Batteries in, switch on (SYS/MOT LEDs light).
  • Join Wi-Fi XRP-<id>, WPA2 xrp-wpilib. The SSID is also in xrp-status.txt on the PICODISK USB drive. With two XRPs on, check this so you're joining the right one, and label each robot with its SSID.
  • XRP IP 192.168.42.1. Web UI http://192.168.42.1:5000 (Wi-Fi mode/AP channel). Robot-code port 3540.
  • Both robots default to the same 192.168.42.1 on their own APs. Run one at a time per laptop, or put both in station mode on a lab router with distinct IPs.

4. RobotPy setup (2026.x, latest on PyPI is 2026.2.1.1)

pyproject.toml. In 2026 the key is components (it replaces robotpy_extras):

[tool.robotpy]
robotpy_version = "2026.2.1.1"
components = ["xrp", "apriltag"]
requires = []

python -m robotpy sync          # installs robotpy + robotpy-xrp + robotpy-apriltag
python -m robotpy sim --xrp     # runs robot.py on the laptop, talking to the XRP

The robot code runs on the laptop through the simulation framework, and the sim GUI shows up even when the XRP isn't connected. Set these before running (or in robot.py via os.environ before import xrp):

HALSIMXRP_HOST=192.168.42.1
HALSIMXRP_PORT=3540

Check: the sim GUI shows the gyro/accelerometer values changing when you move the robot.

5. First-drive robot.py

Channel mapping follows the WPILib XRPReference example (left motor 0, encoder 4/5; right motor 1, encoder 6/7). The right motor is inverted.

import os, math
os.environ.setdefault("HALSIMXRP_HOST", "192.168.42.1")
os.environ.setdefault("HALSIMXRP_PORT", "3540")

import wpilib, xrp
from wpilib.drive import DifferentialDrive

WHEEL_DIAM_M = 0.060
COUNTS_PER_REV = 585.0          # 12 CPR motor-shaft encoder * 48.75:1 gearbox (XRPReference)
DIST_PER_COUNT = math.pi * WHEEL_DIAM_M / COUNTS_PER_REV

class MyRobot(wpilib.TimedRobot):
    def robotInit(self):
        self.left = xrp.XRPMotor(0)
        self.right = xrp.XRPMotor(1)
        self.right.setInverted(True)
        self.drive = DifferentialDrive(self.left, self.right)

        self.lenc = wpilib.Encoder(4, 5)
        self.renc = wpilib.Encoder(6, 7)
        for e in (self.lenc, self.renc):
            e.setDistancePerPulse(DIST_PER_COUNT)
        self.gyro = xrp.XRPGyro()
        self.pad = wpilib.XboxController(0)   # any gamepad in the sim GUI "Joysticks" slot 0
        self.timer = wpilib.Timer()

    def _reset(self):
        self.lenc.reset(); self.renc.reset(); self.gyro.reset()

    def robotPeriodic(self):
        wpilib.SmartDashboard.putNumber("L m", self.lenc.getDistance())
        wpilib.SmartDashboard.putNumber("R m", self.renc.getDistance())
        wpilib.SmartDashboard.putNumber("yaw deg", self.gyro.getAngle())

    def teleopInit(self): self._reset()
    def teleopPeriodic(self):
        self.drive.arcadeDrive(-self.pad.getLeftY(), -self.pad.getRightX())

    # 1 m straight test with heading hold
    def autonomousInit(self):
        self._reset(); self.timer.restart()
    def autonomousPeriodic(self):
        d = (self.lenc.getDistance() + self.renc.getDistance()) / 2
        if d < 1.0 and self.timer.get() < 8.0:
            turn = -0.02 * self.gyro.getAngle()     # sign: check on the bench
            self.drive.arcadeDrive(0.5, turn)
        else:
            self.drive.stopMotor()

UNVERIFIED: exact RobotPy method names for XRPGyro (getAngle() vs getAngleZ(); both exist in Java) and the arcade sign conventions. Check in sim first. Pass test: tape-measured distance is 1.00 m ±3 cm, heading within ±3°.

6. Calibration

  • Wheel diameter: nominal 60 mm. Push the robot 2 m along tape and compare the encoder distance. true_diam = 0.060 * (2.0 / measured).
  • Counts/rev: 585 per wheel revolution (the WPILib XRPReference value, measure on both robots: 12 counts per motor-shaft rev × 48.75:1 gearbox = 585; UNVERIFIED against a motor datasheet). Check by marking a wheel and turning it 10 revs by hand, which should read about 5850 counts per side.
  • Track width (10-turn spin test): spin in place at low speed (for example arcadeDrive(0, 0.5)) until the gyro reads 3600°, then stop. track_width = (|L_dist| + |R_dist|) / (2 * 10 * 2π) * 2, which simplifies to (|L|+|R|) / (20π). Repeat in both directions and average. Nominal is about 155 mm (UNVERIFIED). Check the gyro total against a tape mark on the floor; if the gyro and the floor disagree, fix the gyro scale first.
  • Gyro drift: robot still for 60 s after reset(), then log the yaw. Expect < 1°/min (UNVERIFIED). If it's higher, let the board warm up and keep it still at power-on (the firmware calibrates at boot, UNVERIFIED).

7. Mounting the Pi Zero 2 W + OV9281

Power: use a separate USB power bank (recommended).

  • The XRP V1 (vision robot) has a single 5 V buck regulator rated at about 3 A total (SparkFun forum answer), shared by all 4 servo headers. The Qwiic ports are 3.3 V only, not 5 V.
  • The 4xAA pack also feeds the motors. Motor stall/accel current plus a 0.6–1 A Pi load on alkaline or partly drained NiMH makes 5 V brownouts and Pi resets likely. Neither SparkFun nor WPILib documents servo-header current per pin, and wiring a Pi from a servo header (5 V/GND only) is undocumented (UNVERIFIED, not recommended).
  • Use a small 5 V ≥ 2 A USB power bank (Pi Zero 2 W + OV9281 is about 0.4–0.8 A, UNVERIFIED) into the Pi's PWR micro-USB. Check that the bank doesn't auto-shut-off at low load.

Mechanical

  • Use the XRP chassis grid holes / top deck (snap-in or M3 standoffs, hole size UNVERIFIED). Mount the Pi flat on standoffs above the controller; strap the power bank low and centered over the axle, slightly forward of the caster line.
  • Keep the CG low and between the wheels and the caster. The battery bank is the heaviest part, so put it low.
  • Camera: rigid bracket, forward-facing, about 10–15 cm lens height (suggestion) so it sees tags mounted at that height. Keep the pitch near 0° so the robot-to-camera transform stays simple. Measure robotToCam (x, y, z from the wheel-axle center at floor level; yaw/pitch) with calipers and record it.
  • The CSI ribbon (Zero uses the 22-pin narrow end) should be strain-relieved and kept clear of the wheels. Put a heatsink on the Pi.
  • For the first test a bench-mounted camera with the tag on the robot is still the M4a option (see the test plan).

8. Networking

  • Default: both the laptop and the Pi join the XRP AP (XRP-<id>, 192.168.42.x). The laptop runs robotpy sim --xrp, and the robot program there is the NT4 server. The Pi is an NT4 client pointed at the laptop's IP.
  • The Pico W / RM2 soft-AP supports only a few clients (CYW43 soft-AP is commonly cited as about 4, UNVERIFIED), and throughput is modest. Send only the small pose packet (/vision/tag_data), never video. Keep the client count at 2.
  • Alternative: in the XRP web UI set the XRP to join a home/lab router (station mode), and put everything on that LAN. That needs HALSIMXRP_HOST updated to the XRP's new IP.
  • Addresses: the XRP AP doesn't appear to offer DHCP reservations (UNVERIFIED), so use static IPs: laptop 192.168.42.10, Pi 192.168.42.20 (outside the DHCP pool, UNVERIFIED pool range; check the leases first). Or use mDNS: Pi hostname.local and the laptop's .local name. Mixed Windows mDNS can be flaky, so prefer a static IP for the NT server address on the Pi.
  • Pi NT client: ntcore.NetworkTableInstance.getDefault().setServer("192.168.42.10"); startClient4("pi-vision").

9. AprilTag pose fusion (summary of /workspace/fpga-apriltag-xrp-test-plan.md)

  • Topic: /vision/tag_data (double[]), 10 doubles per tag: [id, x, y, z, qw, qx, qy, qz, ambiguity, margin], published atomically per frame. /vision/timestamp (int, capture time in NT µs). /vision/tags (Pose3d[] struct) is for AdvantageScope only.
  • Estimator: DifferentialDrivePoseEstimator(kinematics(track_width), gyro Rotation2d, L, R, initialPose). update() every loop with gyro + encoders.
  • Translation-only first: take XY from vision and the heading from XRPGyro. addVisionMeasurement(pose, ts, (0.5*k, 0.5*k, 1e6)) with k scaling with distance/tag count. Add the vision heading (std about 0.9 rad) only after the full-3D path is validated.
  • Timestamps: convert NT capture µs into the FPGA-timestamp seconds base (ts = capture_us/1e6, using the NT server-time-synced value). Reject a future timestamp or an age > 300 ms.
  • Reject if: the jump from the current estimate is > 1.0 m; |yaw rate| > 120°/s; the pose is outside the field; single-tag ambiguity > 0.1 at > 1.5 m. Count accepted/rejected on SmartDashboard.
